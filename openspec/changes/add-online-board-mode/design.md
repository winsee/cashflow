## Context

见 [proposal.md](proposal.md) 的 Why。这里只记录会决定怎么写代码的几条既有约束：

1. **状态 = `reduce(RoomState(), 事件流)`，没有例外。** `RoomSession.restore()` 与 `_revert()` 都是从**空的 `RoomState()`** 起把事件重放一遍（`server/app/rooms.py:48`、`:190`）。因此任何新状态——对局模式、棋子位置、牌堆——只要重放时得不出来，撤销一次就会把它抹平。
2. **撤销 = 丢掉几条事件后整流重放。** `_revert` 不写反向事件，它挑出要撤的 seq、把剩下的重放一遍。这条性质可以直接白拿：**牌堆只要是从事件推出来的，撤销就自动把牌退回原位**，不需要写任何「退牌」逻辑。
3. **服务端摇骰子已有先例。** `_dice_gamble_event`（`engine.py:585`）在 decide 阶段摇、把点数写进事件 payload，重放时不再摇。掷骰移动照抄这个做法。
4. **每回合的两把锁已经在了。** `turn_square_used`（本回合已停过一格）、`turn_payday_used`（本回合已结算）是房间级标志，快车道进场当回合的行为就靠它区分（CLAUDE.md ㉔）。纯线上模式不新造一套回合锁。
5. **卡库不动。** `raw` 逐字原文正是为纯线上渲染卡面准备的（design/06 §2）；`data` 是引擎唯一取数来源。这个 change 不加字段、不加 subtype。

## Goals / Non-Goals

**Goals:**

- 纯线上模式下，一局游戏从建房到分出胜负全程不需要任何线下道具。
- 线下辅助模式的代码路径**一行不改**——两种模式在引擎里靠一个模式判断分叉，而不是分裂成两套实现。
- 棋盘、骰子、牌堆全部可重放、可撤销，与既有事件溯源模型同构。
- 演出层（动效）与权威状态彻底解耦：动效播不播、播到哪，都不影响账。

**Non-Goals:**

- 不做棋盘编辑器、不做自定义棋盘。
- 不做动效的美术资源管线（贴图/骨骼动画）——用矢量与 CSS 能做到的质感为准。
- **不做音效**——见 D11 末段，留到棋盘与动效落地之后单独一轮。
- 不改任何既有 REST/WS 协议的语义，只往状态里加字段、往动作表里加动作。
- 不为纯线上模式单独做一套服务端（同一进程、同一房间模型）。

## Decisions

### D1. 对局模式存在事件里，不只存在数据库列里

**决定**：房间创建时追加一条 `ROOM_MODE_SET { mode }` 事件，作为该房间事件流的第一条；`RoomState.mode` 默认 `OFFLINE_ASSIST`。`room` 表加 `mode` 列只作为大厅列表查询的缓存。

**为什么**：`_revert` 从空 `RoomState()` 重放。模式若只存 DB，第一次撤销之后重放出来的 state 就退回默认模式，纯线上房间会当场变成线下房间。

**替代方案**：把模式塞进房主的 `PLAYER_JOINED` payload——省一个事件类型，但把房间属性挂在玩家事件上，语义错位，且房主被移除/转让时容易出事。否决。

**向后兼容**：升级前的房间事件流里没有这条事件，重放得到默认值 `OFFLINE_ASSIST`，正是我们要的。

### D2. 牌堆 = 事件里的一串 id，撤销自动退牌

**决定**：

- `RoomState.decks: dict[str, list[str]]`（牌堆，`[0]` 是堆顶）与 `discards: dict[str, list[str]]`。
- **四副牌**：机会·小生意、机会·大买卖、市场风云、额外支出。职业卡**不进这个模型**（它不洗回、不弃牌、一人一张就没了，见 D14）。
- `START_GAME` 时（仅纯线上模式）追加 `DECKS_SHUFFLED { orders: {deck: [card_id...]} }`，洗牌在 decide 阶段用 `_dice_rng` 同源的 RNG 摇出，牌序整串写进 payload。
- 发牌 `CARD_DRAWN` 的 payload 不变（已经带 `card_id`），`apply` 时从对应牌堆弹出堆顶。
- 牌堆空了要发牌时，先追加 `DECK_RESHUFFLED { deck, order }` 再 `CARD_DRAWN`。
- 卡结算完（`CARD_RESOLVED`/`CARD_PASSED` 等既有终态事件）时把该 id 压入 `discards`。

**为什么**：这样「撤销一次发牌 → 牌退回堆顶」不需要写任何代码——重放时跳过那条 `CARD_DRAWN`，牌自然还在堆顶。撤销跨越洗回也同理，重放的结果天然等价于「那次发牌从未发生」。

**替代方案**：只在事件里存随机种子，重放时用种子重摇。看着更省空间，但要求 RNG 实现、调用次数、Python 版本三者永远一致，任何一处变动都会让历史房间重放出不同的牌。否决——事件溯源的价值就在于事件里写的是**结果**不是**过程**。

**代价**：`DECKS_SHUFFLED` 一条事件约 194 个短 id（几 KB），一局最多再洗几次。可以接受。

**保密**：牌序绝不出房间边界——否则打开 DevTools 就能看到下一张是什么。**堵一个口子不够，事件 payload 有三条对客户端敞开的通道**：

1. `serialize()` —— 只下发各牌堆的剩余/弃牌张数；
2. `broadcast_state(last_events=events)`（`rooms.py:97` → `:277` 的 `"lastEvents"`）—— 每次行动都把刚产出的事件原样广播；
3. `log_rows()`（`rooms.py:359` 的 `"payload": payload`）—— 日志页把历史事件 payload 逐条下发。

后两条是 `DECKS_SHUFFLED` 的真实泄露路径：开局那条含 194 个 card_id 的洗牌事件会直接广播给全员，
打开日志页即可看到整副牌的顺序。**决定**：加一个按事件类型脱敏的共用函数
`_sanitize_payload(etype, payload)`，剔除 `DECKS_SHUFFLED.orders` / `DECK_RESHUFFLED.order`
（换成同名的张数字段），在 `broadcast_state` 与 `log_rows` 两个出口各调一次。
事件流本身（SQLite、重放、`_revert`）照旧存完整牌序——**脱敏只发生在出口，不在存储**。

### D3. 位置存两个字段，不存一个

**决定**：`PlayerState.rr_position: int`（内圈格索引）与 `ft_position: int | None`（快车道格索引）。进快车道时 `ENTERED_FASTTRACK` 事件把 `ft_position` 置为入口格，`rr_position` 不再使用。

**为什么**：一个 `position` 字段配一个「当前在哪条轨」的判断，等于把 `phase` 的信息复制了一份，两处不同步就是 bug。分开存，取哪个由已有的 `phase` 决定，没有第二个真相源。

**编码：1-based 格索引，`0` = 起点/入口标记本身（不是格子、没有效果）。** 这一条必须写死，
因为两条轨道的第 1 格都是**有效果的普通格**——`rat_race.json` 的 `squares[0]` 是「机会」，
`fast_track.json` 的 `squares[0]` 是 `ft-d-forest`（一个梦想格）。若开局就置 `rr_position = 1`，
等于全场站在机会格上却不抽卡；进快车道若置 `ft_position = 1`，玩家凭空占了一个梦想格。

- 开局 `rr_position = 0`（「开始」箭头，在第 24 与第 1 格之间），第一次掷 N 点走到 `squares[N-1]`。
- 进快车道 `ft_position = 0`（「在此进入」箭头，在第 48 与第 1 格之间），下一次掷骰才踏上第 1 格。

这与 D6「入口不是一格，是『第 1 格从哪儿数』」是同一句话，只是把它落到了状态编码上。
呈现层把 `0` 画成环外的那枚三角，不占格位（design/09 §3.5 本来就是这么画的）。

### D4. 掷骰移动是一次动作、一串事件

**决定**：新动作 `ROLL_DICE { diceCount }` 产出的事件序列固定为：

```
DICE_ROLLED { player_id, rolls, dice_count, total }
  → （逐格前进，每经过一个结算格）PAYDAY / FT_PAYDAY   ← 与既有结算完全同一种事件
  → PLAYER_MOVED { player_id, track, from, to, path }
  → （落点是自动格时）落点自身的事件（CARD_DRAWN / CHILD_ADDED / …）
```

**为什么**：

- 结算日复用**既有的 `PAYDAY` 事件**（连同 `_d_payday` 里算钱的那段逻辑抽成共用函数），账目实现只有一份，说明书示例回归自动覆盖两种模式。
- `PLAYER_MOVED` 带完整 `path`，前端才能逐格走位、在正确的格子上弹出入账反馈，而不用自己按点数推路径（推错了就和服务端的结算不对应）。
- 事件粒度这么切，撤销一次掷骰 = 撤掉这一整串（沿用 `_market_cascade` 那种「一批一起撤」的既有做法）。

**结算日不能走 `PAYDAY` 动作**：`_d_payday` 有 `_require_payday_free` 单回合锁，而一次移动可能经过两个结算格。所以抽出的是**共用的算钱函数**，动作层的锁留给线下模式；纯线上模式下 `PAYDAY` 动作本身被拒绝（玩家不能自己点结算）。

**付不出钱时**：某次经过的结算算出付不出到期款项，按既有规则产出 `PAYDAY_UNPAYABLE + BANKRUPTCY_STARTED`，**移动就地终止**，棋子停在那个结算格上。不继续走完剩余点数——人已经进清算了，再走一格触发一张卡毫无意义。

**这一批的边界怎么圈**：`_market_cascade`（`rooms.py:119`）确实是可以照抄的形状，但它是**按 `card_id` 关联的
市场卡专用逻辑**，不是通用批机制——掷骰批没有一个类似的关联键，得自己定：

> 从被撤的 `DICE_ROLLED` 那条 seq 起，到**下一条 `TURN_ENDED` 或下一次 `DICE_ROLLED`**（取先到者）之前的
> 连续 seq 区间，即为这一批。房间级锁保证批内不会被其它玩家的行动插入，但**别人对市场卡的答复会插进来**（见下）。

**两个 cascade 会嵌套**：批内可能有落点发出的 `CARD_DRAWN`，那张若是市场卡，它自己还带一个
`_market_cascade`（伴随事件 + 别人几秒后才提交的答复，后者不限于紧邻范围）。所以撤销掷骰批的算法是
「先圈连续区间，再对区间内每条市场卡 `CARD_DRAWN` 并入 `_market_cascade` 的结果」。
别人已对该市场卡做出实质答复时，沿用既有的 `MARKET_RESPONDED` 拒绝——只是纯线上模式下本人更正已被禁用（D10），
这条拒绝只会落在房主身上，房主可再决定是否连别人的答复一起撤。这一条要有回归钉死。

### D5. 落点用 `RoomState.landing` 表达「现在轮到你处理这一格」

**决定**：`RoomState.landing: Landing | None`，形如 `{ square_id, type, ref_id, resolved }`。

- **自动格**（银行结算日、现金流量日、市场风云、额外支出、孩子、失业、税务审计、离婚、官司）：落点事件当场产出，`landing.resolved = True`，`turn_square_used = True`。
- **选择格**（机会 → 选大/小；慈善 → 捐/不捐；绿格 → 买/不买；粉格 → 买/加价/占位/获胜）：`landing.resolved = False`，等玩家动作。既有的 `CHARITY`、`FT_BUY_BUSINESS`、`FT_BUY_DREAM` 等动作原样复用，只是在纯线上模式下多一道「你确实停在这一格」的校验。
- 新动作只加一个：`CHOOSE_DEAL_SIZE { size: SMALL | BIG }`，选完立刻从对应牌堆发牌。

**为什么不复用 `turn_square_used` 一个布尔**：那个标志只回答「本回合还能不能再停一格」，回答不了「你停在哪一格、还欠一个什么决定」。前端要照设计稿「任何时刻只强调当前该做的那一步」，就必须能从状态里读出这一步是什么。

**校验方向**：纯线上模式下，`FT_BUY_BUSINESS` 之类的动作 SHALL 校验 `landing.ref_id` 与请求的格子一致；线下模式下这道校验跳过（玩家本来就是自己声明停在哪一格的）。这是两种模式在引擎里唯一的分叉形态——**一个 `if mode == ONLINE` 的前置校验**，不是两套实现。

**落点未决时能不能结束回合：按格子类型定**（房主定案）。`_d_end_turn`（`engine.py:177`）现在只拦
未结算的强制卡（`EXPENSE_EVENT/CASH/CREDIT_OPTION/INSTALLMENT/STOCK_EVENT`），拦不住
「停在机会格却不选大小生意就结束回合」。纯线上模式下补一道 `landing.resolved == False` 的判断，
**闸门只对「必须做」的格子落下**：

| 落点 | 未决时结束回合 | 依据 |
|---|---|---|
| 机会格（未选大/小，或选了未抽） | **拒绝**（`LANDING_UNRESOLVED`） | 说明书停在 Deal 格就要抽一张，不是可选项 |
| 慈善事业格 | 允许 | 捐不捐本来就是玩家的选择，不捐 = 什么都不做 |
| 快车道绿格 / 粉格 | 允许 | 买不买本来就是玩家的选择 |

自动格不进这张表——它们落点即 `resolved = True`。前端对「允许」的两类在结束回合的二次确认里
写明「你放弃了这次捐款/购买」，避免误点（`ConfirmDialog` 既有形态，不新增弹层）。

### D6. 棋盘数据升级为结构化格子，并进校验脚本

**决定**：

```jsonc
// rat_race.json
{ "squares": [ { "id": "rr-01", "type": "OPPORTUNITY" }, … ] }   // 24 格
// fast_track.json 增加 squares（businesses/dreams 清单原样保留）
{ "squares": [ { "index": 1, "ref": "ft-d-forest" },
               { "index": 12, "ref": "ft-s-cashflow-day" }, … ],   // 48 格
  "businesses": [...], "dreams": [...], "specials": {...} }
```

内圈类型：`OPPORTUNITY / PAYDAY / MARKET / DOODAD / CHARITY / CHILD / UNEMPLOYMENT`。

**快车道已按上面的结构落地（2026-08-08）**，与本节初稿的 `ring` 设计有两处出入，都是"能推出的不存"：

- **没有逐格的 `id`**——`index` 就是身份，1..N 连续由加载器校验；
- **没有逐格的 `type`**——`ft-b-` / `ft-d-` / `ft-s-*` 前缀已经把类型说尽了。
  五个特殊格 id 固定为 `ft-s-charity / cashflow-day / tax-audit / divorce / lawsuit`，
  对应引擎里早就有的 `FT_CHARITY / FT_PAYDAY / FT_TAX_AUDIT / FT_DIVORCE / FT_LAWSUIT`。
  没有 `ENTRY` 类型：入口不是一格，是"第 1 格从哪儿数"，已由 index 表达。

`tools/validate_cards.py` 增加棋盘校验：格数、各类型计数（内圈 12/3/3/3/1/1/1）、index 连续、`ref` 与企业/梦想清单**双向**对账（清单里的每一条都必须出现在环上恰好一次，环上的每个 `ref` 都必须存在）。快车道部分已实现（`check_fast_track_board()`），内圈部分随 `rat_race.json` 结构化一起做。

**为什么进同一个校验脚本**：CLAUDE.md 已经把「改完卡库必跑 `validate_cards.py`」立成硬门槛，棋盘数据现在也成了引擎取数来源，理应受同一道闸。

### D7. 快车道环的顺序要从棋盘照片补录，且**必须**人工核对

`design/05` 只有绿格/粉格的清单，**没有它们在环上的排布**；内圈序列虽有，但 design/05 §1 自己标了 ⚠️「右列个别相邻格的先后顺序建议在模式二开工前对实物再核对一次」。这两笔数据是纯线上模式的地基，录错的后果是每一次落点都错，而且错得很隐蔽（游戏照常能玩，只是格子不对）。

**决定**：把「补录 + 逐格核对」作为独立的第一批任务，由房主对着实体棋盘走一圈确认，然后才开工引擎。
（原计划产出一张可打印核对页，实际两条轨道都由房主直接对着实物走完，核对页没做也不需要了。）

**两条轨道均已核实通过（2026-08-08）**：快车道 48 格见下；内圈 24 格的顺序确认与 `rat_race.json`
现有序列一致，design/05 §1 那个 ⚠️ 可以撤掉——**顺序不用改，1.2 只是给每格加上 `id` 与 `type`**。

**快车道部分已完成（2026-08-08）**：从 `docs/游戏棋盘.jfif` 分段放大逐格读出 48 格，房主对实物核实通过，落进 `squares`，见 design/05 §3.3。修正两处：

- **现金流量日只有 3 个**（第 12/28/44 格），不是 design/05 v0.1 记的 4 个。
- 补录初稿把快车道描述成「双环」（外环 + 绕转盘的内环），**房主纠正：实体就是一个圈**——格子太多，长方形盘面一圈沿外缘摆不下，才在底边中间向内绕了一段，是排版不是轨道。走法上没有分叉，第 48 格接回第 1 格。design/09 §3.5 的「同一只轮盘」照旧成立，无需为此改呈现。

自洽性证据（已写进 `test_board.py`）：企业恰好 18、梦想恰好 23 一个不多不少；除特殊格插入处外绿粉严格交替。

### D8. 棋盘是一只放射轮盘，内联 SVG，动效用 CSS/WAAPI，不引第三方库

**决定**：棋盘是一段内联 SVG 的**放射轮盘**——内圈 24 个扇形格（每格 15°、缝 1.5°，外径/内径 134/94，中径 114），围着一个可用直径 180px 的轮心；快车道是同一只轮盘，格子多一倍、环收窄一半（外径/内径 140/114），中心因此更大，正好摞下两粒骰。格子是 `<path>` 扇环，棋子是 `<g transform>`，动效走 CSS transform + Web Animations API。

几何常量（`V`/`R1`/`R0`/`RMID`/`RPAWN`）**一处定义**，棋盘渲染与走格动画共用——改半径不会漏掉哪一边。环按格数自己重新分角，格数与顺序改了不用动一行呈现代码。

**为什么圆的**：老鼠赛跑就是仓鼠轮，圆形是这个游戏的字面意思，实体棋盘的内圈本来也是 24 个扇格围着中心。画成方格阵列，等于把它最认得出的那样东西丢了。（第一版画的确实是 24 格矩形网格，看过实物才推翻。）

**为什么内联 SVG**：

- 项目已有内联 SVG 的先例（`QrCode.vue` 自绘矩阵），且 PWA 严格离线、不依赖 CDN。
- SVG 的 DOM 能直接挂点击热区、`aria-label`、Vue 过渡，Canvas 这些都要自己造。
- 已经背了 13MB 的 tesseract 资源（CacheFirst 运行时缓存），再引一个动画库/渲染引擎不划算。

**替代方案**：Canvas/PixiJS 能给更炫的粒子。但格子只有 20~50 个、棋子最多 6 个，SVG 的性能绰绰有余，而「大厂感」在这个体量上靠的是节奏、层次与克制，不是粒子数量。

### D9. 演出层是一个从 `lastEvents` 派生的队列，权威状态先落地

**决定**：新增 `web/src/stage.ts`，与既有 `receipts.ts` **同一个入口**——从 WS `state.lastEvents` 派生演出步骤（掷骰 → 逐格 → 入账 → 发牌 → 翻牌），推进一个可跳过的队列。Pinia store 里的权威状态**在演出开始前就已是最终值**，演出只控制「界面此刻显示到哪一帧」。

**为什么**：这是既有代码里已经验证过的形状（`receipts.ts` 从 `lastEvents` 派生回执、用「换快照前的旧状态」比对，重连首帧 `type:'snapshot'` 不带 `lastEvents` 所以天然不误播——见 CLAUDE.md ㉒）。同一套机制直接给出了「重连不补播动效」这条要求，不用另写。

**节拍表**：9 拍、单次完整序列约 3.2s（走 6 格、无过站），逐拍时长见 design/09 §5.1。顿拍比时长重要。

**跳过 / 减少动效** 三条出口，全部走同一个「清空队列 + 刷到最终状态」：

1. **点击跳过**——每一拍都能被一次点击终止。**是终止到终态，不是加速**：玩到第 20 轮的人不该被自己看过 20 遍的动画拖住。
2. **`prefers-reduced-motion: reduce`**——队列长度恒为 0，整条序列压成一次 120ms 淡入，棋子直接出现在落点。
3. **设置里的「跳过动画」开关**——存 localStorage、**不进房间状态**（它是这台设备的偏好，不是房间的事实），默认关。

三者同一条出口，不会出现「跳过后界面停在中间帧」。

### D10. 纯线上模式关掉的入口，服务端也要关

**决定**：纯线上房间下列入口一律在服务端拒绝——

| 入口 | 拒绝理由 |
|---|---|
| `recognize` / `recognize-text` 两个接口 | 没有实体卡可拍 |
| `DRAW_CARD` 带 `cardId` | 牌只能从服务端牌堆按顺序发（D2） |
| `SELECT_PROFESSION` 传 `professionId` / 已有职业者重复提交 | 职业由服务端随机发、不可重抽（D14） |
| `PAYDAY` / `FT_PAYDAY` 动作 | 结算是走格的结果，不是玩家能点的（D4） |
| `SET_TURN_ORDER` | 回合顺序由服务端掷骰排定（D15） |
| `PLAYER_CORRECT`（本人当回合更正，FR-29） | 见下 |

**为什么 `PLAYER_CORRECT` 也要关**：FR-29 的语义是「抽错卡当场重选」——那是线下认错**实体**卡才会有的事。
纯线上不可能抽错，而牌堆模型下更正一次发牌会把牌退回堆顶（D2），再抽**必然是同一张**，
玩家只会陷入「撤了又抽到一样的」的困惑循环。落点决策失误的出口改由「房主撤销掷骰整批」承担（D4），
房主撤销在两种模式下都照常可用。

**为什么这些都要在服务端**：前端隐藏挡不住直接发请求。纯线上模式的公平性完全建立在
「随机源只在服务端、结果只写进事件流」上，这些口子必须在服务端焊死。

**注意 `SELECT_DREAM` 不在这张表里**：梦想是玩家自己选的（说明书 P.2 步骤 9「选择您的梦想」），两种模式都一样，这个动作照常开放。

### D11. 视觉方向：不另起皮肤，把「大厂感」花在四件事上

沿用既有暖光纸感与阶段换肤（房主已定，见 memory「UI 重设计定案」与 CLAUDE.md ①）。棋盘的高级感来自：

1. **材质**——棋盘是一块有厚度的纸板：格子有极细的压印边、轻微的纸纹、棋子有接触阴影。不是纯色方块拼图。
2. **节奏**——每个动作有起-承-转-合：骰子滚 → 定格（顿一拍）→ 棋子起步 → 逐格（每格有轻微的落点感）→ 停 → 卡牌飞出翻开。顿拍比时长重要。
3. **层次**——同一时刻只有一个东西是亮的：轮到谁，谁的格子和棋子有光；卡牌翻开时棋盘压暗一档。
4. **一致的反馈语言**——金额永远绿加红减、永远从数字原位浮起、永远同一条缓动曲线。既有 `flash()` 队列与回执体系原样复用。

**零新增视觉 token**：没有引入任何新的颜色、字号、圆角或阴影，全部取自 `web/src/style.css`。新增的只有轮盘、棋子、骰子、牌背四个物件，材质规则也是既有那三条：纸片底 `--panel`、暖色发丝线 `--line`、`--shadow-sm` 投影。新增类统一 `.wheel` / `.board-*` 前缀。

**棋盘留在纸上，不引入实体那块紫板**：紫是实体棋盘的底色，但在这套米色界面里它是外来户。板底走 `linear-gradient(168deg, var(--panel), var(--panel2))` + `--line-2` 描边，和三种卡面同一种材质。留在纸上白得一件事——**快车道换 `.skin-ft` 金箔肤时棋盘自己跟着变金**，因为它引用的就是会被覆盖的那两个变量，一行都不用为它另写。（若当初选了紫板，这里就得为快车道单开一套。）

**音效不在本轮**（design/09 §11）：动画节拍还在调的时候做音效，只会把音画对不上的问题固化下来。留到棋盘与动效落地后单独一轮。

### D12. 纯线上另起一套页面骨架：棋盘主视图 + 三档抽屉，取消常驻标签栏

**决定**（design/09 §2）：纯线上房间不复用四标签页，改为 HUD（现金/月现金流 + 目标进度 + 轮次与本轮行动顺序座次条）→ 棋盘 stage → 底部抽屉三档：

| 档位 | 高度 | 用途 | 棋盘 |
|---|---|---|---|
| peek | 128px | 一行状态 + 主 CTA（掷骰 / 结束回合 / 等待别人） | 完整可见 |
| half | 46dvh | 卡面与决策、落点选择、求购要约、股票交易 | 等比缩小到装得下，整块仍完整可见 |
| full | 88dvh | 破产清算、账本三页、快车道格子选择器 | 贴顶对齐，只留顶部一线 |

- **档位由内容决定**，不由用户记忆决定。用户可拖动覆盖，但下一次系统事件会重新提档，且**提档只升不降**——别人抽的市场卡要我答复时，不能因为我刚把抽屉推下去就把这件事藏起来。
- 抽屉展开时棋盘**不加遮罩**（还要看别人的位置），只缩尺寸。
- **决策按钮钉在抽屉底**（`position: sticky`）：一张牌堆卡加上前后对比预览就超过 half 档的高度，内容必须能滚，但「买入 / 放弃」不能跟着滚走。
- **取消 tabbar**：报表/总览/日志收进棋盘右上角的「📋 账本」（点开即 full 档 + 分段控件），说明书是第二个悬浮按钮。它们是「随时可查」而不是「本回合待办」，本就不该和棋盘平级。
- 抽屉与既有弹层分工照旧、不新增规则：**我的待办 → 抽屉**；**别人的动作波及到我 → `BaseModal`**（压在抽屉之上）；**二次确认 → `ConfirmDialog`**。

**为什么不做「一套界面两种配置」**：线下界面的主干是引导式待办，因为 App 不知道你在哪，只能一次问一件事；纯线上棋盘就是空间上下文，照搬待办流等于让玩家面对一串没有上下文的问句。折中的结果是两边都不好用。代价是纯线上要另写一套骨架——线下模式因此完全不受影响，反而更干净。

**两个实现约束**（设计稿里踩过）：① 档位切换缩的是**棋盘自身的宽度变量**，不是 `transform: scale`——stage 有 `overflow: hidden`，缩 stage 会连裁切框一起缩，棋盘照样被裁在原位置，白缩一场；② 正因为 stage 不再有 transform，**悬浮工具挂在 stage 内部的右上角**最稳（挂在页面根上要用魔数避开 HUD，HUD 一加高就被挡住）。

### D13. 撤销：撤掷骰才动棋子，撤抽卡不动棋子

**决定**：`_revert` 撤掉一次 `DRAW_CARD` 时，棋子位置**不回退**——位置由掷骰那一串事件决定，抽卡不改它。撤销后抽屉回到「落点未决」态，全屏发牌序列**不重播**（那是过去时的演出，不是当前待办）。只有撤销掷骰本身，才把位置、经过的结算、发出的牌整批回退（D4 已定：一次掷骰的整串事件一起撤）。

**为什么单独立一条**：这在事件流层面是自动成立的（牌堆和位置各由各的事件推出），但**在 UI 上极易做错**——一旦棋子跟着跳回去，玩家会以为骰子也白摇了，下一步就会去点已经用掉的掷骰按钮。这条要有回归钉死。

### D14. 职业卡由服务端发，梦想仍由玩家选

说明书 P.2「简明步骤」这两件事用的是不同的动词，不是行文随意：

> 4. 每位玩家**抽**一张职业卡；
> 9. 在「快车道」上**选择**您的「梦想」，并将奶酪置于「梦想」格之上；

**决定**（房主定案：时机与位置都不变，只换发牌方式）：

- **职业**——`SELECT_PROFESSION` 这个动作**保留**，还在房间准备页、还由玩家自己触发，只是在纯线上模式下：① 忽略客户端传来的 `professionId`；② 服务端在 decide 阶段从**尚未被占用的职业**里随机挑一张；③ 结果写进既有的 `PROFESSION_SELECTED` 事件（payload 本就带 `profession_id`/`title`/`data`，`_a_profession_selected` 一行不用改）；④ **已经抽过的玩家再次提交一律拒绝**——既有实现允许反复改选（`test_flows.py` 有 A 改选的用例），纯线上必须把这条堵上，否则"随机"等于可以刷。
- **梦想**——`SELECT_DREAM` 两种模式都照常开放，引擎零改动，玩家手动挑。纯线上模式只改呈现：在房间准备页打开快车道棋盘点粉格选，选中即在该格中径插一枚自己颜色的圆点。那枚圆点就是实体游戏里放上去的奶酪，`DREAM_TAKEN` 唯一性校验照旧。

**为什么职业不能让玩家挑**：12 张职业卡工资从 $1,600 到 $13,200，差 8 倍（医生 13,200、经理 4,600 是 design/02 §3 的回归基准）。让玩家从列表里挑，开局平衡当场失效，而且与说明书的「抽」不是一回事。这本质上和 `DRAW_CARD { cardId }` 同一类问题——**由玩家声明线下发生了什么**，D10 已经把这类入口全部焊死，职业卡只是之前漏掉的一个。

**线下辅助模式为什么不动**：那边 `SELECT_PROFESSION` 是**录入你摸到的那张实体卡**，不是挑（FR-5 原文：「玩家抽实体职业卡后，在手机上从职业列表中选择（或拍照识别）自己的职业」）。语义本来就是对的，连"可以改选"都是对的——录错了当然要能改。

**为什么职业不走 D2 的牌堆模型**：牌堆模型解决的是「反复发、发完洗回、撤销要退回原位」。职业卡一人一张、不洗回、不弃牌，建一副堆只是把简单事情复杂化。随机源用 decide 阶段的 RNG（与 `_dice_gamble_event` 同一种做法），结果写进事件，重放不再摇——事件溯源要的「写结果不写过程」已经满足。

**顺带白得的一条**：撤销一次抽职业后重抽，会抽到（可能）不同的一张——这正是撤销的本意。牌堆模型下反而必然是同一张，那才是错的。

**呈现**：准备页那个按钮从「选择职业」变成「抽职业卡」，点完翻出 `ProfessionCard` 卡面（复用 D9 的翻牌序列）。抽过之后按钮消失，位置换成自己的职业卡。

### D15. 回合顺序由服务端掷骰排定

`_d_start_game`（`engine.py:157`）现在硬要求先有 `turn_order`，拿不到时抛的错就是
**「请先线下掷骰并排定回合顺序」**——这是一次不折不扣的「玩家声明线下发生了什么」，
和 `DRAW_CARD { cardId }`、`SELECT_PROFESSION { professionId }` 是同一类，之前漏掉了。
说明书 P.2「开始游戏」1 写的也是每人掷骰、点数最大者先行。

**决定**（房主定案）：

- 纯线上模式下 `SET_TURN_ORDER` **拒绝**（进 D10 那张表）。
- `START_GAME` 的 decide 阶段替全员各摇一次骰，点数最大者先行、按点数降序排；**平局者之间重摇**，
  直到分出先后。随机源与做法同 `_dice_gamble_event`（`engine.py:585`）：decide 阶段摇、结果写进 payload、
  重放不再摇。
- 事件类型**复用既有的 `TURN_ORDER_SET`**（`_a_turn_order_set` 一行不改），payload 在既有的 `order`
  之外补一个 `rolls`（含重摇轮次）纯作审计与呈现之用。`START_GAME` 在纯线上模式下**先产出
  `TURN_ORDER_SET` 再产出 `GAME_STARTED`**，`_d_start_game` 里那道 `if not state.turn_order` 的校验
  因此在纯线上模式下要挪到「摇完之后」——不是删掉。
- 线下辅助模式一个字不改：那边房主录入的是**线下真的掷出来的**顺序，语义正确。

**呈现**：开局瞬间在棋盘中央播一次「全员掷骰定先后」的短序列（复用 D9 的骰子拍），
点数与最终座次写进 HUD 的行动顺序座次条（design/09 §2 已有这条）。

## Risks / Trade-offs

- **棋盘顺序录错 → 每次落点都错，且不易察觉** → D7：补录 + 人工核对作为前置任务，校验脚本做双向对账兜住「漏格/多格/引用不存在」这类错，顺序错只能靠人眼。**两条轨道均已由房主对实物核实通过（2026-08-08）**，这条风险已关闭；结构化时不得顺手调整顺序。
- **牌堆状态进 `RoomState` 后撤销行为退化** → 牌堆完全由事件推出（D2），并新增回归：撤销一次发牌后下一次发出的必须是同一张；撤销跨越洗回后重放结果必须与当前状态一致。
- **两种模式共用引擎，改动误伤线下模式** → 硬约束：既有 451 条测试一条不改、一条不跳。模式分叉只允许以「前置校验」的形态存在（D5），不允许出现两份算钱逻辑。
- **一次移动经过多个结算日，逐月/逐次结算的顺序错了会算错钱** → 复用既有 `PAYDAY` 事件与算钱函数，并补「一次移动跨两个结算日」「跨结算日时破产」两条用例；`PAYDAY_UNPAYABLE` 只审计不动账的既有语义不变。
- **动效让人等** → 全程可跳过（D9），且默认时长按「比你想的短一点」调；`prefers-reduced-motion` 直接零动效。演出永远不阻塞服务端状态。
- **棋盘在小屏手机上挤掉操作按钮** → 棋盘与操作区分层（D12）：棋盘在自己的容器里按档位缩尺寸，主操作常驻在抽屉里、决策按钮钉底，页面本身不横向滚动（这是既有设计稿踩过的坑，CLAUDE.md 里 RoomView 按钮被卡片挤出首屏修过一次）。文字溢出不靠肉眼查——截图脚本跑完扫一遍 `scrollWidth > clientWidth` / `scrollHeight > clientHeight` 的元素并列出来（跳过可滚容器与 SVG 内部）。
- **撤销后棋子跳回去** → D13：撤抽卡不动棋子，配回归钉死。
- **`DECKS_SHUFFLED` 事件体积** → 几 KB/局，SQLite 无压力；换来的是重放绝对确定，值。
- **牌序从事件广播/日志接口泄露** → 出口脱敏（D2），并把「未发出的牌序不出现在房间状态、事件广播、日志接口」
  三处一起写进 card-decks 的验收 Scenario。只测 `serialize()` 会漏掉真正的那两个口子。
- **撤销掷骰批时漏撤或多撤**（尤其批内含市场卡、别人已答复） → D4 末段定死了区间规则与 cascade 嵌套顺序，
  回归里补「掷骰 → 落在市场风云格 → 别人答复 → 房主撤掷骰」这一条。
- **慈善骰子粒数按赛道不同**（老鼠赛跑 1–2 粒 3 轮、快车道 1–3 粒永久，见 `models.py:115/151`）
  → 粒数校验必须读 `phase`，两条赛道各一条非法粒数用例，别写成一个 `1 <= n <= 3`。

## Migration Plan

1. **数据先行**：补录并人工核对两条棋盘序列，跑通新增的棋盘校验。此时不影响任何线上行为。
2. **DB**：`room` 表加 `mode TEXT NOT NULL DEFAULT 'OFFLINE_ASSIST'`（`CREATE TABLE IF NOT EXISTS` 之外补一条幂等的 `ALTER TABLE`，失败即忽略——既有 schema 就是这个风格）。既有房间自动落到线下辅助。
3. **引擎**：加状态字段与新动作，全程保持既有测试绿。
4. **前端**：建房加模式选择 → 棋盘视图 → 演出层。纯线上入口在跑通 `ui-smoke` 前不出现在大厅。
5. **回滚**：前端撤掉建房时的模式选项即可——服务端的新字段对线下房间是惰性的（默认值 + 不产出相关事件），已建的纯线上房间可以让房主结束对局。事件流不需要回滚。
