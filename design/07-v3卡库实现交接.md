## 2. 阻断性不兼容（必须先修，否则一个测试都跑不起来）

### 2.1 🔴 重复卡被拒绝入库 —— `server/app/data_loader.py:123-142`

```python
raise DataValidationError(f"{source} 重复卡「{title}」…：标题与数值完全相同，不能入库")
```

**旧假设**：标题+数值全同 = 录入错误 → 拒绝。这个假设来自只有 14 张种子卡的时代。
**新事实**：实体牌堆里**本来就有 9 组共 20 张完全相同的卡**（见 06 §5），这是真实的牌堆构成，
直接决定抽牌概率。删掉它们游戏就不对了。

**改法**：把「重复 = 报错」反转为「重复 = 正常，但必须显式标注」：
- 内容相同的卡必须有相同的 `key`，且第 2 张起必须有 `duplicateOf` 指向首张；
- 缺 `duplicateOf` 才报错（防的是真·录入重复）；
- 洗牌时按实际张数放入，**不要**按 `key` 去重。

`tools/validate_cards.py` 里已实现这套判定，可直接搬。

### 2.2 🔴 `LOSS_EVENT` 已并入 `EXPENSE_EVENT` —— `engine.py:176, 300, 358, 379`

v3 里 `LOSS_EVENT` 这个 subtype **不再存在**。四处引用全部改为 `EXPENSE_EVENT`。
（两者字段形状本就相同，schema 里一直是同一分支处理，合并无行为变化。）

### 2.3 🔴 `condition` 已拆分 —— `engine.py:340-347, 359, 382`

```python
cond = d.get("condition")        # ← 字段已不存在
```

拆成了两个语义不同的字段：
- `payerCondition`：判定**玩家**够不够格（`hasChildren` / `hasRentalProperty` / `hasRealEstate`）
- `assetCondition`：判定**资产**够不够格（`cashflowPositive`，仅 mk-032 求购旅馆用）

`_condition_met()` 改读 `payerCondition`；新增 `assetCondition` 的判定用于市场卡筛选资产。
注意 `hasRealEstate` 是 v3 新增的取值（bd-038 用），旧代码只认前两个，会抛 `BAD_CONDITION`。

### 2.4 🔴 求购计价字段变了 —— `engine.py:235`

```python
price = d["pricePerUnit"]        # ← 字段已不存在
```

v3 改为 `priceBasis` + `price` 两个字段，且 **`priceBasis` 有三种取值，算错基准最大差 13 倍**：

| priceBasis | 单价乘以什么 | 卡数 |
|---|---|---|
| `PER_UNIT` | 1（整个资产） | 22 |
| `PER_ROOM` | 资产的 `rooms`（2/4/8） | 10 |
| `PER_PIECE` | 资产的 `quantity`（金币枚数） | 2 |

**这是本次升级最容易算错钱的地方**，务必先写测试再改代码。

### 2.6 🔴 录入库会覆盖运行时库 —— 数据丢失风险

`server/data/entry/cards/` 是**录入工具的活动库**（不是死数据），`POST /api/entry/publish` 会把它**整体覆盖**到运行时库：

```python
for deck, items in staged.items():
    _save_file(_runtime_file(deck), items)   # 录入库 → 覆盖 cards/
```

它现在装的还是 **20 张旧 schema 种子卡**（缺 `key`/`source`/`raw`）。后果：

1. **录入工具整体不可用**——加卡、发布预览、发布全部报 `'key' is a required property`；
2. **一旦有人补齐字段让校验通过，点「发布」就会把 194 张卡冲成 20 张**；
3. 录入进度统计（`entry.py:105`）拿录入库张数当分子，会显示「小生意已录 9 张」而实际 56 张。

**建议处理**：把录入库整体替换为运行时库那 194 张卡。录入库的设计定位就是"编辑区"，
运行时库是"发布结果"；既然全量卡已经录好，编辑区就该是这 194 张，之后改数值走
「录入工具改 → 预览 diff → 发布」才闭环。替换后跑一次 `/api/entry/publish/preview`，
diff 应为空，即证明两库一致、发布是安全的空操作。

## 3. 引擎需要新增的能力

### 3.1 资产模型缺字段 —— `server/app/engine/models.py`

`RealEstate` 目前只有 `asset_type / cost / down_payment / mortgage / cashflow`，
**没有 `rooms` / `units` / `quantity`**，导致按间/按套/按枚计价根本无法实现。

需补：

| 字段 | 用途 | 来源 |
|---|---|---|
| `rooms` | 公寓房间数 2/4/8，PER_ROOM 计价 | 卡的 `data.rooms`（15 张） |
| `units` | 公寓楼套数 12/24/60，PER_UNIT 计价与 `minUnits` 门槛 | 卡的 `data.units`（4 张） |
| `quantity` | 收藏品枚数，PER_PIECE 计价 | 卡的 `data.quantity`（2 张） |
| `business_kind` | 企业细分类型，指名求购匹配 | 卡的 `data.businessKind`（4 张） |
| `income_category` | 现金流记入记录卡哪一行 | 卡的 `data.incomeCategory`（51 张） |

### 3.2 五个全新 subtype（引擎完全没处理过）

| subtype | 卡 | 要做什么 |
|---|---|---|
| `DICE_GAMBLE` | sd-013 嫂子借钱 | 扣 \$5,000 → 服务端掷 1 骰 → >3 得 \$10,000，否则无收入。**骰子结果必须记入事件流**（可重放），不可重掷 |
| `COLLECTIBLE` | sd-036 / sd-053 金币 | 按 `quantity` 持有的资产，无现金流，靠 PER_PIECE 求购卡变现 |

## 5. 测试要求（先写测试再改代码）

在 design/02 §13 现有清单上追加 13 条，**每条都对应一个真实会算错钱的场景**：

1. **按间计价**：持 8 室公寓遇 mk-020（PER_ROOM \$40,000）→ 结算 **\$320,000**，不是 \$40,000
2. **套数门槛**：持 8 套公寓楼遇 mk-015（minUnits=12）→ 不可售；持 24 套 → \$720,000
3. **只付一套**：持 3 套 8 室公寓遇 bd-003 → 只扣 **\$2,000**（现有代码会扣 \$6,000）
4. **抽卡人限定**：bd-038 只扣抽卡人，其他持房玩家不动账
5. **买家范围**：非抽卡人买 `DRAWER_ONLY` 股票 → 拒绝；买 2BIG / CD → 允许
6. **利息入账**：买入 CD 后「利息」栏 +\$20，「股利」栏不变
7. **负现金流资产**：买入 bd-041 后月现金流**减少** \$100
8. **零首付**：买入 sd-031 现金不变、负债 +\$50,000、月现金流 +\$100
9. **并股/拆股**：股数减半/翻倍而**总成本不变**，事件期间交易窗口关闭
10. **骰子赌局**：sd-013 固定种子下点数 4/5/6 得 \$10,000，1/2/3 无收入
11. **企业细分匹配**：持 sd-018（小型机械公司）遇 mk-033（求购软件公司）→ **不可**售；遇 mk-025 → \$50,000；遇 mk-008 → 月现金流 +\$250
12. **土地变现**：持 sd-017（\$5,000 买入）遇 mk-026 → 可售 \$150,000
13. **分期收款**：mk-029 第 1–199 月现金流 −\$500 且未入账；第 200 月恢复且现金 +\$100,000；中途破产时挂账按已扣月数比例折算

## 7. 三条不要重蹈的坑

数字化过程中我犯过三次**同一类错误**：把卡面的叙述文字当成游戏机制。记录在此：

1. ~~「目前没有其他买主」= 该资产不可转售~~
   → 那是剧情文案（解释没人跟你抢），它在卡面上占的位置正是别的卡印售价区间的那行，
   真实含义只是「未印转售参考价」。已并入 `priceIndeterminate`。

2. ~~「卖 \$25,000 要先还 \$300,000 抵押、净亏 27.5 万，所以不是同一标的」~~
   → **出售始终是可选的**，报价低玩家拒绝即可，"卖了亏"不构成匹配矛盾。
   **引擎硬性要求**：`MARKET_SELL_OFFER` 只推要约、绝不自动成交，
   **也不得因"卖了会亏"而过滤或隐藏要约**——玩家可能为了套现渡过破产危机而主动贱卖。

3. ~~「可以通过条款取得银行贷款」= 该卡特有的贷款许可~~
   → 说明书 p6：「您可以向银行贷款，**除非您被宣布破产**」，这是全局规则。已删 `loanAllowed`。

**给新会话的建议**：看到卡面某句话想加字段时，先问一句「这是规则，还是氛围？」
`raw` 已完整保存原文，`data` 里塞不必要的字段只会让引擎多出错误分支。
`tools/validate_cards.py` 里有一份**已删字段黑名单**，加回去会直接报错。
